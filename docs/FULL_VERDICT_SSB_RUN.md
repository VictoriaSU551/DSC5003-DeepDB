# Verdict SSB SF2 execution controller

The v1/v2 planning descriptions below are historical. The actual v2 run completed only its independent SQLite oracle, then failed during PostgreSQL startup. Its namespace remains TAINTED. The current v3 is a separately reviewed operational repair; no Verdict execution result is claimed by this document.

This is a separate operational extension of the frozen candidate protocol. It implements a concrete **SF2-only** small gate. There is no formal/SF500 execution command. Compilation, SQLite, PostgreSQL startup/connect and original Java calls remain unexecuted until root reviews the exact plan/source SHA and provides an approval file. Plans and inspections alone are not original-engine results.

## Reviewed operational design

Use only the completed native SF2 benchmark (N=11,997,996, n=39,587) and its complete four dimensions, after the candidate's pinned physical lineage check. Do not regenerate any SSB input or recreate the removed full-fact temporary tables. First stream these five inputs into a new SQLite database and execute the 19 distinct sample queries (13 raw + six original SUM projections), retaining exact integer SUMs, NULL, complete group keys and timings. Store both sample SUM × actual N/n and sample SUM × native generator 1/p as rational oracles. No full-population answer is passed to registration or the engine. Full truth is only a later statistical comparator.

Only `deepdb_verdict_ssb` may be created/written. Reject existing user objects; do not drop or replace tables/databases. The previous `deepdb_job` and `deepdb_verdict` are inspected only through system-catalog identities before/after. That check is not a per-row content proof. Reject other client activity in the cluster before creating/importing the owned DB and before the scientific lock interval. Keep PostgreSQL startup separate from initialization: reuse the existing project PG11.5 cluster, never run initdb/install or edit server config. Root can request startup through the approved operation; no automatic shutdown affects an externally started server.

Import dimension data into the four full `public` tables with their primary keys. Keep `public.lineorder` empty and without a primary key. COPY 17 fact columns directly into the augmented uniform sample, preserving duplicate rows; the auxiliary default expressions use actual n/N and original PostgreSQL `mod(cast(round(random()*100) as integer),100)` after fixed `setseed`. No duplicate raw fact heap is required. Register only this fact sample through original public metadata APIs with SampleParam ratio n/N. Dimensions remain unregistered `nosample`, with no vpart/vprob columns.

Hold one explicit transaction SHARE lock over empty fact, retained sample and all full dimensions during **all 38** calls. Lock metadata relations too after registration. Each native call runs the unmodified `VerdictJDBCContext.execute` exactly once; a new isolated Java context/process records its actual `A query to db:` rewrite from original debug logging, raw cells, errors, elapsed time and stderr. The controller does not pre-rewrite SQL with a substitute algorithm. The source planner, full dimension policy and physical rewrites must agree. An engine error is captured and remains a support gap, not a successful adapter point. Original raw compound SUM predictions remain separate from the two-SUM point adapter; no combined CI is emitted.

Compare raw Q1–Q3 no-bound results and the Q4 two-SUM adapter against exact retained-sample SUM × N/n, with declared tolerance `rel_tol=2e-12, abs_tol=1e-6` for original double arithmetic. Preserve full truth/missing/extra/NULL/nonfinite groups and native CI95 outcomes separately. A raw Q4 mismatch is retained as the previously observed compound-expression risk, never silently replaced. CI point/halfwidth are original native values; missing/null/nonfinite intervals remain unavailable. SF2's small retained groups need not all have finite native variance estimates.

## Resources and isolation

The proposed, root-reviewed **SF2-only** cap is 1 GiB for new own DB + SQLite/staging/output + positive cluster WAL disk growth + positive cluster `pgsql_tmp` growth, sampled throughout import/Java calls. Existing reusable runtime/source archives are not newly duplicated. Record WAL generated bytes separately from physical WAL growth. Never attribute whole-C-drive free-space change to this task while the native generator writes elsewhere. Minimum startup available RAM/free disk are 4 GiB/4 GiB; Java RSS limit 1 GiB, Python RSS limit 512 MiB; statement timeout 120 s, work_mem 16 MiB, temp_file_limit 128 MiB per backend. The loop is a measured bound with finite polling windows; the backend temporary-file limit is an additional guard. No global PG configuration changes or registry/system installs occur.

PostgreSQL storage is separate from the 16 GiB SSB data/output allowance. SF2 measurements inform a new formal allowance; this plan grants none. Root should complete the gate then stop its started PostgreSQL before formal RSPN requires at least 5 GiB available memory. The controller does not stop a server it did not start.

## Transactions, evidence and recovery

Claim a new namespace with atomic mkdir; persist RUNNING before work. Any input/hash/resource/operational exception makes it TAINTED and refuses automatic restart. Preserve raw errors and partial outputs; no existing successful or failed namespace is overwritten. Each physical query has exact mode/role/SQL/index identity and an atomic receipt. Final publication requires rechecking current source/runtime/raw descriptors and protected catalog identities. The outer lifecycle is PASS only after final result/seal publication; a result without outer PASS is provisional.

The read-only verifier must neither import psycopg2 nor connect to SQLite/PG or execute a process. It requires the exact independent output set, full source/runtime/input closure, each of 38 identities, all raw per-call files, original metadata/import/oracle evidence, process logs and persistent lifecycle. Empty/subset/duplicate maps and altered/resealed query content must fail. Compiled Java is included once it exists, but is currently **UNCOMPILED**. No SF2 support or timing claim is made before real execution.

Direct COPY is checked by exporting all original columns in physical insertion order and comparing canonical CSV bytes/hash/row count against the bounded raw-source normalizer, including fact duplicates. Exact native metadata must contain only the fact sample with n/N (full dimensions must not be registered). The original name suffix is rounded to four decimals; original `DbmsPostgreSQL.insertEntry` uses `Double.toString` for the actual metadata ratio, independently of that suffix. The checker does not round the actual ratio. Result receipt verification recomputes each raw decoding and actual rewrite, checks SQL/role/index identity and the exact required set, and independently rederives rational oracle weights. Stored full-population error/CI statistics do not participate in the sample-scaling correctness gate.

The immutable closure includes 400 pristine original source files, the fixed executable JAR, all 446 JDK files, all 1,436 selected PG runtime files, their fixed archives, local Python runtime/stdlib/psycopg2 bytes, candidate/controller/Java/test/protocol files, and the accepted physical SF2 input artifacts. No shared scientific file is patched. Child Java commands clear external agent/classpath environment overrides and fix locale/timezone. OS transitive Windows libraries remain platform dependencies; the plan records platform and Python hash environment.

Any failure leaves a TAINTED namespace and owned DB for explicit review; there is no automatic DROP/retry or washing of partial results.

## V3: observed Windows startup failure and completed-oracle adoption

Root's actual `sf2_golden_v2` run completed five SQLite loads and all 19 distinct exact sample queries in 12.875 seconds. Its database is 43,941,888 bytes, SHA256 `f0e1cb60ecfff25bc30ffb5d6c06d54d5ed8d09dbfa1ea95403837f3f3a4f908`. No PostgreSQL import, Java compilation or Verdict query was reached. The original controller used `subprocess.run(capture_output=True)` for `pg_ctl start`. Root observed the project postmaster alive, pg_ctl already absent, no import receipt and no other PG clients. After independently verifying the exact project postmaster identity, root stopped only that owned server with direct file stdout/stderr; pg_ctl stop returned 0 in 0.156 seconds. Releasing the inherited pipe handles immediately let the original Python call return `TimeoutExpired` and naturally write TAINTED. This evidence agrees with the project's CPython 3.8 Windows implementation: its timeout path calls a second unbounded `communicate()` after killing pg_ctl, while inherited pipe writers can prevent reader-thread EOF.

The failed run, original v2 plan/freeze, root recovery JSON, oracle bytes and logs are preserved. The exact v2 controller/test/protocol source snapshots are retained under `output/full/verdict_ssb/v2_failed_source/`; their SHA values match the previous freeze. V3 does not resume or overwrite that namespace.

All v3 pg_ctl operations redirect stdin to DEVNULL and stdout/stderr to exclusive, newly created binary files. They never use PIPE/capture_output. The start/status/stop timeouts remain 90/15/90 seconds. A process receipt, elapsed time, returned output and failure state are retained even on a timeout. This removes the observed pipe-EOF dependency; it is not a claim that arbitrary filesystem or operating-system failures cannot occur.

Before startup, v3 requires `pg_ctl status` code 3 and an absent `postmaster.pid`, then atomically records a start intent. Success and exception paths both inspect the PID file and actual Windows process. Automatic ownership requires the project postgres executable, exact `-D` project cluster, port 55432, positive PID, matching PID-file/process creation epochs and creation within this particular start window. Existing/old/foreign or unproven servers are never adopted. A verified new identity is assigned before receipt publication, so even a startup timeout or receipt failure can reach the original failure cleanup. Cleanup rechecks the same complete identity and absence of external clients before stop. Any ambiguity leaves UNRESOLVED_NOT_OWNED/TAINTED for root; it never triggers an unowned stop. Final read-only verification binds and checks all pg_ctl raw files/process receipts, startup intent and ownership evidence, including their exact required set.

The optional `--reuse-oracle-from sf2_golden_v2` is an explicit, narrow adoption of only the already completed independent oracle. Its five JSON SHA values, original v2 source snapshots and physical SQLite SHA are fixed constants.
